# 2.0.63 — 共用料桶登記後自動分攤

## 結果與規則

共用料桶的未確認分量原先一律留作待分攤，跨批號紙本只能看到整桶參考量。本版依紀錄日期各棟的存欄頭數比例，自動歸到各棟所屬批號，更新飼料清單、到料統計、肉豬紀錄表、PDF、列印與CSV。

正式專案使用 `FEED_AUTO_ALLOCATION=headcount`。可選政策為 `headcount`、`equal` 或留空；留空保留舊版手動行為。原先已有人工確認 `bin_allocations` 的紀錄優先沿用，不覆寫。舊的未分攤紀錄直接適用衍生規則，沒有複製或重填到料、沒有重寫原紀錄。補登歷史頭數或更正飼料總量後，尚未人工確認分量自動重算。

頭數使用紀錄當天日終存欄，包含當日死亡、出豬、淘汰等已登記異動，較晚日期不影響較早分量。已明確指定的進場前批次按進場頭數分攤。原總量為整公斤時分至整公斤，尾差給最後一個正頭數棟；有小數公斤則保留原精度，各棟合計守恆。無法確定批次、頭數未知或多個候選批次時保留待核對，不捏造頭數。

例：共用桶供1、2棟，頭數100／300，4噸分為1／3噸。1棟與18棟同批時，1噸歸該批，2棟3噸歸另一批。原始4噸只有一筆，料桶庫存只增加4噸。報表涵蓋整個共用桶且進場前狀態一致時，整桶在紙本只列一次；跨批或單棟才分列其份額。不同進場前狀態仍各自分段。

自動歸屬的是到料量，沒有當成實測耗料。原本未確認共享耗料仍不憑這個估算算出實測FCR；直接耗料照原登記值、到料粗估料肉比沿用估算標示。未來紀錄會列入完整紙本，到該日期才增加目前庫存。

## 修改與一致性

- `app/feed_allocation.py`：政策、依日期頭數、自動批次比對、分量計算與守恆。
- `app/feed.py`：單一共用桶歸屬、各批報表分段、完整同桶紙本去重。
- `app/weekly.py`：回傳報表使用的自動分攤政策。
- `app/feed_review.py`：一般、批次及照片共用的核對預覽回傳自動分量；確認憑證納入政策與分量，過期頭數或政策不能沿用原預覽。
- `app/server.py`：飼料API、統計、CSV與前端政策狀態。
- `app/review.py`：已可自動歸屬者不再誤列未指定飼料待補。
- `app/operations.py`：操作版本憑證包含分攤政策。
- `app/static/feed-receipts.js`、`feed.js`、`feed-review.js`、`feed-bulk.js`、`feed-drafts.js`：核對畫面及清單顯示自動分量，中越語說明，人工分量仍可維護。
- `.env.example`、部署及使用文件、2.0.63版本／快取標記。

沒有資料庫結構或SQL變更，結構仍為4。正式農場紀錄沒有新增、更新或刪除；原ID、總量、照片來源、備註與稽核保留。現有交易、權限、同鍵重試、照片確認、庫存安全容量機制沿用。

## 驗證

- `scripts/check.sh`：794個單元／整合測試及JavaScript語法檢查通過。
- `test_auto_feed_allocation.py`：32個SQLite／合成Hrana情境，最終整桶合併顯示調整後再跑32個通過。含頭數依日期、更正與刪除、人工優先、原總量守恆、找出唯一批次、未知不猜、預覽過期、同鍵重試、前置飼料、實耗不捏造、同桶紙本一次、實體庫存不重複、唯讀權限。
- `auto_feed_allocation_browser.py`：7個情境通過，實際一般表單不用手填分量，確認前列0.5／1.5噸，丟失回覆重試只有一筆，原筆更正刪除同步，HTML／PDF／CSV只列所屬份額，中越手機介面無溢出。
- `feed_bulk_browser.py`：7個情境通過，原整批輸入、人工確認量與重試相容。
- `feed_drafts_browser.py`：8個情境通過，原照片待確認、確認後才正式寫入與失敗重試相容。
- `weekly_all_records_browser.py`：使用實際正式模式 `FEED_AUTO_ALLOCATION=headcount FEED_ORDERS_ARE_ARRIVALS=1`，8個情境通過，白板合成24筆78噸依正確批次完整列出，未來資料、批號優先、PDF／CSV與原筆修改同步保留。

共30個瀏覽器情境。使用隔離合成農場、真實HTTP與Chromium；沒有正式農場登入測試、正式測試紀錄、實際通知、LINE或付費AI。A4產物為實際PDF，未使用實體印表機驗證。
